# Content Factory — CLAUDE.md
> Файл маршрутизации контекста и правил поведения роя агентов.
> Все субагенты обязаны прочитать этот файл перед началом работы.

## ОБЯЗАТЕЛЬНО ЧИТАТЬ ПРИ СТАРТЕ КАЖДОЙ СЕССИИ

1. `CLAUDE.md` (этот файл)
2. `PROJECT_STATE.md` — текущий статус проекта, приоритеты, нюансы реализации
3. `ai-clone/rules.md` — голос и стиль автора
4. `ai-clone/feedback/*.md` — жёсткие ограничения из прошлых ошибок

Читать без напоминания пользователя. Это базовый контекст для любой работы.

## КОМАНДА «ЗАПОМНИ ЭТО»

Когда пользователь пишет «запомни это» — немедленно:
1. Определить что именно обсуждалось и какое решение принято
2. Дописать это в `PROJECT_STATE.md` в нужный раздел
3. Закоммитить: `git commit -m "memory: [краткое описание]"`
4. Подтвердить пользователю что сохранено и где именно

Это приоритет — выполнить до любых других действий в этом сообщении.

## ОБЯЗАТЕЛЬНО ОБНОВЛЯТЬ PROJECT_STATE.md

После каждого значимого действия обновить `PROJECT_STATE.md`:
- Задача выполнена → отметить статус, убрать из приоритетов
- Принято архитектурное решение → зафиксировать с обоснованием
- Появился новый нюанс или ограничение → добавить в раздел «Важные детали»
- Изменились переменные окружения или зависимости → обновить соответствующий раздел

Обновление `PROJECT_STATE.md` — часть каждого коммита, не отдельный шаг.

## 5. Маршрутизация контекста для субагентов

Каждый субагент при старте ОБЯЗАН:

1. **Прочитать этот файл** (`CLAUDE.md`)
2. **Прочитать `ai-clone/rules.md`** — правила голоса и стиля
3. **Агрегировать `ai-clone/feedback/*.md`** — список жестких ограничений из прошлых ошибок
4. **Получить задачу от оркестратора** из соответствующего файла в `plans/`

### Контекст по ролям:

| Субагент | Дополнительно читает |
|---|---|
| `lead-orchestrator` | `plans/`, `retrospectives/` (последние 3) |
| `knowledge-retriever` | `knowledge/` (поиск через `scripts/knowledge_search.py`) |
| `web-researcher` | только документация, GitHub repos, инженерные блоги |
| `content-writer` | пакет от `knowledge-retriever` + `business/` |

| `editor-critic` | финальный текст + `ai-clone/rules.md` |
| `deployer-publisher` | готовый MD/MDX-файл |

## 6. Feedback Loop — механика непрерывного обучения

**При обнаружении ошибки** в готовом тексте (человеком или `editor-critic`):

1. Создать файл в `ai-clone/feedback/YYYY-MM-DD_краткое-описание.md`
2. Использовать шаблон:

```markdown
# Ошибка: [Краткое описание]
- **Что пошло не так:** [Описание ошибки ИИ]
- **Почему это ошибка:** [Смысловое или техническое обоснование]
- **Как писать правильно:** [Пример правильной конструкции или инструкции]
```

**Перед каждым циклом генерации** оркестратор (`scripts/orchestrator.py`):
1. Читает все файлы из `ai-clone/feedback/`
2. Формирует блок `## ЖЕСТКИЕ ОГРАНИЧЕНИЯ (из feedback):`
3. Передает этот блок в системный промпт каждого субагента

## 7. Definition of Done для статьи

Статья считается готовой только если:

- [ ] **Information Gain**: содержит оригинальные схемы/таблицы/кейсы/конфиги, которых нет в ТОП-10 выдачи
- [ ] **Chunking-friendly**: иерархия H2-H4, первые предложения каждого блока — емкий ответ (AEO)
- [ ] **GEO-проверка пройдена**: `geo-emulator` подтвердил цитируемость ключевых блоков
- [ ] **Код проверен**: все блоки кода работоспособны, ссылки валидны
- [ ] **Стиль подтвержден**: `editor-critic` не нашел отклонений от `ai-clone/rules.md`
- [ ] **Schema.org**: JSON-LD метаданные сгенерированы и добавлены в шапку

## 10. Работа с ветками Git и сохранение контента

Поскольку бот на продакшене (Render) генерирует новые статьи и сохраняет их напрямую в ветку `main` удаленного репозитория (Git-as-a-CMS), ИИ-агенты при локальной разработке обязаны строго соблюдать регламент синхронизации, чтобы не стереть и не потерять статьи:

1. **При старте новой сессии/задачи:**
   - Сделайте `git fetch origin`
   - Переключитесь на ветку `main` и обновите её: `git checkout main && git pull origin main`
   - Если вы работаете в технической ветке (например, `claude/...`), немедленно влейте в неё актуальный `main` перед началом изменения файлов: `git merge main` (или `git merge origin/main`).

2. **При завершении разработки и деплое нового кода:**
   - Сделайте коммит ваших изменений в текущей рабочей ветке (`claude/...`).
   - Переключитесь на `main`: `git checkout main`.
   - Подтяните последние статьи с продакшена: `git pull origin main`.
   - Выполните слияние вашей рабочей ветки в `main`: `git merge <рабочая_ветка> --no-edit`.
   - Запушьте изменения на GitHub: `git push origin main`.
   - Вся кодовая база на Render и локально должна быть настроена на деплой из `main` (переменная окружения `GITHUB_BRANCH=main`).
