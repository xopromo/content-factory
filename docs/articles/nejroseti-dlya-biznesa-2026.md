## 1. Почему сейчас — экономика изменилась

Внедрение нейросетей в бизнес стало экономически оправданным: стоимость

## 2. Ключевые архитектуры для бизнес-задач

Для 90% корпоративных задач достаточно трёх архитектурных паттернов:
RAG, fine-tuning и агентные системы. Выбор между ними определяется не
модой, а типом данных и допустимым уровнем ошибок.

### 2.1 RAG — стандарт для работы с корпоративными данными

RAG (Retrieval-Augmented Generation) снижает частоту галлюцинаций с ~20%
у «голой» LLM до 3–8% — это результат бенчмарка RAGAS
(arXiv:2309.15217). Механика проста: перед генерацией ответа система
выполняет семантический поиск по базе знаний на основе векторных
эмбеддингов и передаёт релевантные фрагменты в контекст модели.

Это де-факто стандарт для работы с корпоративными документами: контракты,
регламенты, технические спецификации, база прецедентов поддержки. Модель
не «знает» ваши данные — она работает с тем, что вы ей подаёте в runtime.

**Минимальный стек для запуска RAG:**

```python
# LangChain + Qdrant + OpenAI — production-ready пример
from langchain_community.vectorstores import Qdrant
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain.chains import RetrievalQA

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = Qdrant.from_documents(
    documents=docs,
    embedding=embeddings,
    url="http://localhost:6333",
    collection_name="corporate_kb"
)

qa_chain = RetrievalQA.from_chain_type(
    llm=ChatOpenAI(model="gpt-4o-mini"),
    retriever=vectorstore.as_retriever(search_kwargs={"k": 5})
)
```

LangChain (>90k звёзд на GitHub) и LlamaIndex покрывают 80%+
production-пайплайнов. Для векторного хранилища на старте — Qdrant или
pgvector (если уже используете PostgreSQL).

**Когда RAG не справляется:** задача требует понимания тонкого стиля,
специфической терминологии или структуры вывода, которые сложно передать
через контекст. Это сигнал к fine-tuning.

### 2.2 Fine-tuning и LoRA: когда prompting не справляется

Fine-tuning — целенаправленное дообучение языковой модели на ваших данных
— оправдан, если у вас есть более 1 000 размеченных примеров и задача
узкая: классификация обращений, извлечение сущностей, генерация в строго
заданном формате. Ниже этой отметки — few-shot prompting (базовая техника
промпт-инжиниринга) даёт сопоставимый результат при нулевых затратах на
обучение.

Microsoft Research (arXiv:2401.02009) показали: LoRA fine-tuning на 1–5k
доменных примеров превосходит few-shot prompting на узких бизнес-задачах
и догоняет full fine-tuning при 10–20% его стоимости.

**Практический порог принятия решения:**

| Условие | Рекомендация |
|---|---|
| Задача + 0–200 примеров | Few-shot prompting |
| Задача + 200–1 000 примеров | RAG или системный промпт |
| Задача + 1 000–10 000 примеров | LoRA fine-tuning |
| Задача + >10 000 примеров | Full fine-tuning или distillation |

Для LoRA на практике: библиотека `unsloth` сокращает время обучения
Llama 3.1 8B в 2× и потребление памяти на 60% по сравнению с Hugging
Face PEFT. Обучение на 2k примерах на одной A100 — около 40 минут.

```bash
# Установка и запуск LoRA fine-tuning через unsloth
pip install unsloth
# Далее — стандартный Trainer из transformers с параметрами LoRA:
# r=16, lora_alpha=32, target_modules=["q_proj","v_proj"]
```

### 2.3 Агентные системы: AutoGen, LangGraph, CrewAI

Агентные системы — это интеллектуальная автоматизация следующего уровня:
несколько специализированных агентов работают совместно, передавая задачи
и результаты между собой. В production-кейсах (Uber Eats, Booking.com)
такие системы обрабатывают до 40% tier-1 обращений без участия человека.

Microsoft AutoGen (>30k звёзд) — стандарт для multi-agent workflow в
enterprise. LangGraph подходит, если нужен контроль над состоянием и
циклами. CrewAI — быстрее в прототипировании, но менее гибок в сложных
сценариях.

**Когда агенты оправданы:**
- Задача включает более двух шагов с ветвлением логики
- Нужна интеграция с внешними инструментами (API, БД, браузер)
- Требуется параллельная обработка подзадач

**Минимальный пример с LangGraph:**

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict

class AgentState(TypedDict):
    messages: list
    next_step: str

# Определяете узлы (агентов) и рёбра (переходы)
workflow = StateGraph(AgentState)
workflow.add_node("classifier", classify_intent)
workflow.add_node("resolver", resolve_issue)
workflow.add_conditional_edges(
    "classifier",
    route_by_intent,
    {"billing": "resolver", "technical": "resolver", "escalate": END}
)
```

Важное ограничение: агентные системы умножают стоимость инференса на
количество шагов. Задача с 5 агентами и 3 итерациями — это 15
LLM-вызовов. Считайте TCO заранее.

## 3. Бизнес-сценарии с измеримым результатом

Три сценария с доказанным ROI от ИИ в 2024–2025: клиентская поддержка,
аналитика и корпоративный поиск. По каждому — конкретные метрики,
архитектурное решение и реальные результаты внедрения.

### 3.1 Клиентская поддержка: автоматизация tier-1

Автоматизация tier-1 поддержки с помощью чат-ботов на базе ИИ —
наиболее зрелый сценарий с измеримым ROI: 30–60% снижение нагрузки на
операторов при правильно настроенном handoff.

Tier-1 — это типовые обращения: статус заказа, сброс пароля, условия
возврата, стандартные технические вопросы. Они составляют 40–70%
входящего потока в большинстве B2C-компаний. Именно здесь автоматизация
клиентского сервиса с помощью нейросетей окупается быстрее всего.

**Архитектура для поддержки:**

```
Входящее обращение
    → Классификатор интента (LLM, few-shot)
    → Если tier-1: RAG по базе знаний → генерация ответа → отправка
    → Если tier-2+: извлечение контекста → передача оператору с саммари
```

Ключевой параметр качества — confidence threshold для передачи оператору.
Не устанавливайте его выше 0.85 на старте: лучше передать больше — и
обучиться на реальных данных.

**Метрики для оценки:**

| Метрика | Baseline (без ИИ) | Цель (6 мес.) |
|---|---|---|
| % автоматически закрытых обращений | 0% | 35–45% |
| Среднее время ответа (tier-1) | 4–8 часов | <2 минуты |
| CSAT по автоответам | — | ≥4.0 / 5.0 |
| Стоимость одного обращения | $3–8 | $0.50–1.50 |

### 3.2 Аналитика и генерация отчётов

Нейросети и бизнес-аналитика объединяются в сценарии «Text-to-SQL +
нарратив»: LLM сокращают время подготовки аналитических отчётов на
60–80% за счёт автоматизации трёх операций — извлечения данных, их
интерпретации и оформления нарратива.

Этот сценарий даёт наибольший ROI в компаниях, где аналитики тратят более
30% времени на подготовку регулярных отчётов. Модель переводит вопрос на
естественном языке в SQL-запрос, выполняет его, интерпретирует результат.

**Стек:**

```python
# Text-to-SQL через LangChain SQLDatabaseChain
from langchain_community.utilities import SQLDatabase
from langchain_openai import ChatOpenAI
from langchain_experimental.sql import SQLDatabaseChain

db = SQLDatabase.from_uri("postgresql://user:pass@host/dbname")
llm = ChatOpenAI(model="gpt-4o", temperature=0)

chain = SQLDatabaseChain.from_llm(llm, db, verbose=True)
result = chain.invoke("Покажи топ-10 клиентов по выручке за Q1 2026")
```

Критическое ограничение: Text-to-SQL работает стабильно на схемах до
50–100 таблиц. На больших схемах — добавляйте semantic layer (dbt
semantic layer, Cube) или передавайте модели только релевантное
подмножество схемы.

Дополнительный слой — автоматический нарратив поверх данных. Промпт типа
`"Ты бизнес-аналитик. Вот данные: {data}. Напиши executive summary на 150
слов, выдели 3 инсайта."` закрывает задачу без кастомной разработки.

### 3.3 Корпоративный поиск по документам

RAG поверх корпоративной базы знаний — это корпоративный семантический
поиск с ИИ — сокращает время поиска информации сотрудниками на 40–65% по
данным пилотов Slack и Notion Enterprise (2024). Сотрудник задаёт вопрос
на естественном языке и получает точный ответ со ссылкой на источник,
вместо того чтобы искать по папкам.

Это первый сценарий, который стоит запустить внутри компании: данные не
покидают инфраструктуру (при self-hosted векторной БД), ROI виден за
30–60 дней, а обратная связь от пользователей даёт материал для
улучшения.

**Что индексировать в первую очередь:**
- Регламенты и политики (HR, безопасность, finance)
- Техническая документация (API-доки, инструкции к продукту)
- База прецедентов поддержки (closed tickets с решениями)
- Протоколы совещаний (последние 12 месяцев)

**Чанкинг — критический параметр качества.** Стандартный размер чанка —
512–1024 токена с перекрытием 10–15%. Для структурированных документов
(регламенты, договоры) — чанкинг по смысловым блокам, не по размеру.

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,
    chunk_overlap=100,
    separators=["\n\n", "\n", ". ", " "]
)
chunks = splitter.split_documents(documents)
```

Качество поиска измеряйте через Hit Rate@5 (доля запросов, где правильный
документ вошёл в топ-5 результатов). Цель для production — выше 0.85.
Ниже — пересматривайте стратегию чанкинга или embedding-модель.

## 4. Как не провалить внедрение

66% корпоративных AI-проектов не доходят до production — и причина не в
модели, а в отсутствии системного подхода к оценке и управлению рисками
(Stanford HAI AI Index 2025).

---

### 4.1 Почему 66% проектов не доходят до production (Stanford HAI)

Провал происходит на трёх типовых этапах: нет baseline-метрики до старта,
нет eval-пайплайна в CI/CD, нет ответственного за качество модели в
production.

Команды фокусируются на выборе модели — и пропускают вопрос «как мы
поймём, что она работает хуже, чем вчера?». Без ответа на него деградация
обнаруживается только по жалобам пользователей. Это системная проблема
MLOps-зрелости: большинство команд внедряют корпоративный ИИ без
процессов мониторинга, которые давно стандартны в классическом машинном
обучении.

Три симптома обречённого проекта:

| Симптом | Что на самом деле сломано |
|---|---|
| «Модель иногда галлюцинирует» | Нет eval-датасета, нет порога качества |
| «Сложно сравнить промпты» | Нет версионирования промптов |
| «Непонятно, стало ли лучше после деплоя» | Нет A/B-фреймворка для LLM |

---

### 4.2 Evaluation framework: обязательный минимум

Evaluation — это не опция, а инфраструктура. Внедряйте её до первого
деплоя, не после.

**Минимальный стек:**

```bash
# 1. Создайте golden dataset: 100–200 пар (вопрос → эталонный ответ)
# 2. Подключите RAGAS для RAG-пайплайнов
pip install ragas

# 3. Запустите базовые метрики
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_recall

results = evaluate(
    dataset=your_dataset,
    metrics=[faithfulness, answer_relevancy, context_recall]
)
# faithfulness < 0.85 → модель придумывает факты вне контекста
# context_recall < 0.80 → retrieval не находит нужные чанки
```

Для не-RAG задач — `openai/evals` или `EleutherAI/lm-evaluation-harness`.
Оба работают с любыми моделями через OpenAI-совместимый API.

**Четыре метрики, без которых нельзя идти в production:**

| Метрика | Инструмент | Критический порог |
|---|---|---|
| Faithfulness | RAGAS | > 0.85 |
| Latency P95 | LangSmith / Phoenix | < 3 сек для интерактивных |
| Hallucination rate | Custom eval | < 5% |
| Cost per request | LangSmith traces | Определяется бюджетом |

Запускайте eval при каждом изменении промпта или модели — через GitHub
Actions или аналог. Регрессия на 5% по faithfulness до пользователя
доходить не должна.

---

### 4.3 Безопасность и compliance (PII, GDPR)

Отправка персональных данных в облачные LLM — юридический риск по GDPR и
152-ФЗ без дополнительных соглашений с провайдером.

**Практический чеклист перед production:**

```
☐ Data Processing Agreement (DPA) подписан с OpenAI / Anthropic / Azure
☐ PII-маскирование на уровне pre-processing (перед отправкой в модель)
☐ Логи запросов не содержат чувствительных данных
☐ Роль и права доступа к LLM API задокументированы
☐ Retention policy для логов определена и соблюдается
```

Для обработки медицинских, финансовых или персональных данных —
рассмотрите self-hosted вариант: Ollama + Llama 3.1 70B на выделенном
сервере закрывает 80% задач при полном контроле над данными.

Prompt injection — отдельная угроза для агентных систем. Если агент
принимает пользовательский ввод и имеет доступ к инструментам (API, БД),
добавьте слой валидации входных данных до передачи в LLM.

## 5. Стек для старта: инструменты без vendor lock-in

Оптимальный стартовый стек в 2026 — это LangChain или LlamaIndex для
оркестрации, Qdrant или pgvector для хранения, LangSmith или Phoenix для
мониторинга. Все компоненты заменяемы независимо друг от друга.

---

### 5.1 Оркестрация: LangChain / LlamaIndex

LangChain (>90k ⭐ на GitHub) и LlamaIndex — де-факто стандарт для
RAG-пайплайнов. Выбор между ними зависит от задачи:

| Критерий | LangChain | LlamaIndex |
|---|---|---|
| Сложные агентные цепочки | ✓ Сильнее | — |
| Работа с документами / knowledge base | — | ✓ Сильнее |
| Количество интеграций | >600 | >150 |
| Порог входа | Выше | Ниже |

**Минимальный RAG за 15 строк (LangChain):**

```python
from langchain_community.vectorstores import Qdrant
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain.chains import RetrievalQA

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = Qdrant.from_documents(docs, embeddings, location=":memory:")

qa = RetrievalQA.from_chain_type(
    llm=ChatOpenAI(model="gpt-4o-mini"),  # $0.15/1M tokens — дёшево
    retriever=vectorstore.as_retriever(search_kwargs={"k": 5})
)

answer = qa.invoke("Какова политика возврата товара?")
```

Для production — используйте LangGraph вместо устаревшего AgentExecutor:
он даёт явный контроль над состоянием агента и поддерживает
human-in-the-loop.

---

### 5.2 Векторные БД: Qdrant, Weaviate, pgvector

Выбор векторной БД определяется масштабом и существующей инфраструктурой.

| БД | Лучше всего для | Self-hosted | Managed |
|---|---|---|---|
| **pgvector** | Уже используете PostgreSQL, < 1M векторов | ✓ | ✓ (Supabase, Neon) |
| **Qdrant** | Высокая нагрузка, нужен фильтрованный поиск | ✓ | ✓ (Qdrant Cloud) |
| **Weaviate** | Гибридный поиск (vector + BM25) | ✓ | ✓ |
| **Pinecone** | Fully managed, нет DevOps-ресурсов | ✗ | ✓ |

Для старта с объёмом до 500k документов — `pgvector` с индексом `ivfflat`
закрывает задачу без новой инфраструктуры:

```sql
-- Создание колонки и индекса
ALTER TABLE documents ADD COLUMN embedding vector(1536);
CREATE INDEX ON documents USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 100);

-- Поиск ближайших 5 документов
SELECT content, 1 - (embedding <=> $1) AS similarity
FROM documents
ORDER BY embedding <=> $1
LIMIT 5;
```

При росте свыше 1M векторов или при необходимости фильтрации по
метаданным — мигрируйте на Qdrant. Миграция занимает один скрипт
переиндексации.

### 5.3 Мониторинг: LangSmith, Phoenix (Arize)

Без трассировки LLM-вызовов отладка в production — это гадание. LangSmith
и Phoenix (Arize) решают одну задачу разными путями — и оба вписываются в
существующий MLOps-процесс.

**LangSmith** — нативный инструмент для LangChain-стека:

```python
import os
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "ls_..."

# Всё остальное — без изменений. Трассировка включается автоматически.
```

Даёт: полное дерево вызовов, латентность каждого шага, стоимость токенов,
сравнение версий промптов.

**Phoenix (Arize)** — open-source альтернатива, работает локально, не
отправляет данные во внешние сервисы:

```bash
pip install arize-phoenix
python -m phoenix.server.main &  # UI на localhost:6006
```

Оба инструмента поддерживают экспорт в OpenTelemetry — данные можно
направить в существующий Grafana/Datadog стек.

**Минимальные алерты, которые должны быть с первого дня:**

```
☐ P95 latency > 5s → алерт в Slack
☐ Error rate > 1% → алерт в PagerDuty / Telegram
☐ Cost per day > N$ → алерт на email
☐ Faithfulness < 0.80 (еженедельный eval-прогон) → задача в трекер
```

## 6. Что делать прямо сейчас

Начните с одной задачи с измеримым baseline, соберите 100 пар вопрос/ответ
для eval и запустите RAG-прототип на LangChain + pgvector за две недели —
это минимальный путь к работающей нейросети в production. Инструменты
стабилизировались, стоимость инференса упала в 10×, стратегия внедрения
ИИ задокументирована.

**Стартовый план на 2 недели:**

| Неделя | Действие | Результат |
|---|---|---|
| 1, день 1–2 | Определите одну задачу с измеримым baseline (время, качество, стоимость) | Точка отсчёта для ROI |
| 1, день 3–5 | Соберите golden dataset: 100 пар вопрос/ответ для eval | Возможность измерять прогресс |
| 2, день 1–3 | Запустите RAG-прототип на LangChain + pgvector | Работающий proof of concept |
| 2, день 4–5 | Прогоните RAGAS, зафиксируйте метрики | Базовый eval-фреймворк |

Не начинайте с fine-tuning и не выбирайте модель до того, как определена
задача. 80% бизнес-задач решаются RAG + GPT-4o mini или Claude 3 Haiku
без дообучения.

Единственное решение, которое нельзя откладывать — это
eval-инфраструктура. Всё остальное можно поменять: модель, стек,
архитектуру. Отсутствие измерений в production не лечится ретроспективно.
